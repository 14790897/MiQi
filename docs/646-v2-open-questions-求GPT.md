## 一、TaskPolicy 复杂度设计的问题（核心，先说清楚）

### 1.1 当前公式（GPT 第五轮 + 我的落地调整）

```python
complexity_score = 0
if n_tool_calls >= 3:     +1   # 工具数（弱信号，封顶 +1）
if uses_skill:            +3   # Skill 执行（强信号）
if estimated_duration_min > 5: +2
if produces_artifact:     +2   # 产生文件产物（强信号）
if multi_stage_reasoning: +2   # 跨多轮推理（强信号）
# >= 4 → 弹 Plan Card
```

### 1.2 我在落地时遇到的 3 个矛盾（已做取舍，需确认）

**矛盾 A：工具数量到底算不算复杂度？**
- 你的第五轮评审说"工具数量≠复杂度"（查询 20 篇论文标题=10 次搜索，用户不需要确认）
- 但公式里 `>=3 工具 +1` 又依赖数量
- 我的取舍：工具数只 +1 且封顶（弱信号），避免纯读多工具误弹——**是否认可？**

**矛盾 B："生成文件"该不该弹？**
- 你的任务表："生成文件 ✅ 弹"
- 但公式下「搜索+写文件」（2 工具）= 0+2 = 2 < 4 **不弹**
- 我的取舍：**接受不弹**——写文件在 workspace 内可撤销（安全），与 Edit 模式"文件自动放行"语义一致；不可逆操作（上传/删除/支付）由 ActionCard 永远兜底——**是否认可"写文件不是计划卡触发条件"？**
- 反例风险：用户发"帮我写一个自动化脚本"（1 个 write_file）——不弹卡直接执行——**用户可能希望这里有一次确认**（脚本内容用户没看过）

**矛盾 C：多阶段判定（multi_stage_reasoning）当前未生效**
- harness 插桩没有传 multi_stage_reasoning（默认 False）——实际只有"工具数+产物"在起作用
- 模型 5 轮每轮 1 个工具（去重后可能 2-3 个唯一工具）→ 复杂度低估 → 不弹
- **需要**：harness 在累计工具判定时检测"跨轮数"（第 2 轮起就算多阶段？）——还是引入 turn 级轮次计数？

### 1.3 待拍板问题

1. **阈值 4 是否合适**？降阈值（如 2）→ 单写文件也弹（回到旧坑风险）；升阈值 → 更多任务静默执行
2. **artifact 权重**是否按"写类工具数量"递增（写 1 个 +2，写 3 个 +4）？还是保持单次 +2？
3. **纯读大任务**（20 篇总结但不写文件）——按你的"多个来源总结看复杂度"——现在纯读+多阶段=0+2=2 不弹——**用户可能希望这类"大任务"也弹**（确认意图）——要不要给纯读大任务（如 ≥5 个读工具 + 多阶段）加保底分？
